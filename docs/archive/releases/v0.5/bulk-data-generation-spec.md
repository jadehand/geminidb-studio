# GeminiDB Studio v0.5.0 批量造数功能说明

## 版本目标

v0.5.0 只做一件事：把"批量造数"做成一个能实际落地、能给测试同事直接用的功能。

这个版本的原则是：

- 功能完整，但不堆无关能力。
- 界面简洁，默认路径最短。
- 高风险动作必须先预览、再确认。
- 新手看得懂，老用户能快速上手。

## 核心场景

测试同事需要在 GeminiDB / Influx 里快速补造数据，典型需求包括：

- 选定一个 database 和 measurement。
- 指定要造哪些天的数据。
- 给 time、tag、field 填值。
- 对 field 增加简单约束，比如：
  - `latency_avg > ttft_avg`
  - `cnt = rpm`
- 对目标 measurement 不存在的情况，允许先规划、再确认是否创建。
- 当指定的 RP 不存在，或者目标时间已经超出 RP 保留范围时，给出明确提示。

## 界面设计

### 入口位置

推荐把"批量造数"放在侧栏或顶部工具区，优先级高于次要工具，但低于连接和查询主流程。

原因：

- 这个功能属于高频辅助操作，不应该藏得太深。
- 需要先选 database 和 measurement，放在能和目录一起联动的位置最顺手。
- 侧栏入口适合"先选对象，再配置规则"的工作流。

### 入口表现

建议入口文案直接叫：

```
批量造数
```

不要再加更长的说明，因为主界面已经足够复杂。

### 弹窗 / 面板结构

建议使用一个独立弹窗，内部按步骤分区展示，而不是一上来就铺满所有高级配置。

建议结构如下：

1. 目标选择
   - database
   - measurement
   - 目标状态提示
2. 时间范围
   - 最近 N 天
   - 指定某一天
   - 指定某几天
3. 字段配置
   - tag
   - field
   - 时间字段
4. 约束规则
   - 字段间关系约束
   - 简单公式 / 比较
5. 预览与确认
   - 生成计划
   - 查看风险提示
   - 执行写入

## 功能范围

### 1. 目标选择

必须支持：

- 选择 database
- 选择 measurement

建议联动规则：

- 切换 database 后，刷新 measurement 列表。
- 切换 measurement 后，刷新 schema。

### 2. 时间选择

这一块建议统一成"日期集合"概念，而不是只做"最近 N 天"。

需要支持：

- 最近 N 天
- 指定某一天
- 指定某几天

推荐交互：

- 最近 N 天：适合批量生成连续历史数据。
- 指定某一天：适合补单日数据。
- 指定某几天：适合不连续回填。

这里的 N 必须是可选的，不能强制默认填死。

### 3. measurement 不存在时的处理

建议逻辑是：

- measurement 不存在时，先允许进入"计划阶段"。
- 在计划里明确标记为"待创建"。
- 真正执行写入前，必须让用户确认是否创建。

这样做的原因：

- 测试环境经常需要给新 measurement 回填历史数据。
- 直接拦死会削弱功能价值。
- 但直接自动创建也有风险，所以必须二次确认。

推荐展示文案：

- `已选目标 measurement 不存在，执行时将创建`
- 或者 `measurement 待创建`

### 4. tag / field 值配置

建议保留下面几类模式，不要做太多花样：

- 固定值
- 从列表随机取值
- 按规则递增 / 递减
- 从其他字段派生

如果当前版本要尽量收敛，我建议先落地前 3 种，从其他字段派生 和更复杂的脚本型生成放到后续版本。

### 5. field 约束

这个需求值得做，但要限制在"可理解、可预览、可校验"的范围内。

建议支持：

- 字段间比较
  - `latency_avg > ttft_avg`
  - `cnt = rpm`
- 简单数值约束
  - 大于 / 小于 / 等于 / 区间
- 简单依赖
  - 一个字段基于另一个字段生成

不建议在 v0.5.0 做：

- 任意脚本表达式
- 完整编程语言
- 过于自由的函数链

理由很直接：

- 可解释性差。
- 校验成本高。
- 出错后测试同事也很难自己排查。

### 6. RP 提示

这里的 RP 指 Retention Policy，也就是保留策略。

你问到的两句话，意思分别是：

- **指定的 RP 不存在**：目标数据库里没有这个保留策略。
- **数据已超出 RP 保留时间**：你要写入的历史时间点，早于这个 RP 允许保留的数据范围。

比如某个 RP 只保留 7 天数据，你却想回填 30 天前的点，就会落到这个限制里。

建议产品表现上要给出清晰提示，不要只抛底层错误。

## 推荐流程

我建议 v0.5.0 的主流程固定成下面这条：

1. 选 database
2. 选 measurement
3. 选时间模式
4. 配置 tag
5. 配置 field
6. 配置约束
7. 预览计划
8. 确认执行

这个顺序能把复杂度压住，也符合测试同事的真实使用习惯。

## 预览页应展示什么

预览阶段建议至少展示：

- 目标 database
- 目标 measurement
- 选择的日期列表
- 每天计划生成的点数
- tag / field 配置摘要
- 约束规则摘要

预览页不要直接显示太多实现细节，重点是让用户知道：

- 会往哪里写
- 会写哪些天
- 会不会创建新 measurement
- 有没有越过 RP

## 风险控制

### 必须确认的情况

以下情况执行前必须明确确认：

- measurement 不存在，需要创建
- 目标写入时间超出 RP 保留期
- 用户选择的字段约束可能导致部分点无法生成
- 写入模式会覆盖或重复已有数据

### 建议默认安全策略

- 默认不自动执行
- 默认先预览计划
- 默认执行前要求二次确认
- 默认只生成当前用户主动选择的时间范围

## 非目标

v0.5.0 不建议同时做这些事：

- 复杂可视化模板库
- 批量导入外部文件
- SQL 级脚本编排
- 多测量跨库联动生成
- 复杂自动修复器

这些都会把"批量造数"做散。

## 验收标准

v0.5.0 至少要满足下面几点：

- 能选 database 和 measurement
- 时间支持单天、多天、最近 N 天
- measurement 不存在时能在预览里标记为待创建
- field 支持基础约束
- 能提示 RP 不存在或数据超出保留期
- 预览和执行是分开的
- 执行前有明确确认
- 界面不堆冗余控件
