# GeminiDB Studio v0.5.0 批量造数可执行开发清单

## 目标

把"批量造数"做成可用、可预览、可确认执行的功能，版本号统一到 0.5.0。

## 交付范围

### 必做

- 新增"批量造数"入口。
- 支持选择 database 和 measurement。
- 支持时间范围：
  - 最近 N 天
  - 指定某一天
  - 指定某几天
- 支持 tag 和 field 的基础值配置。
- 支持 field 约束，例如：
  - `latency_avg > ttft_avg`
  - `cnt = rpm`
- measurement 不存在时，先在预览里标记为"待创建"，执行前要求用户确认。
- 提示 RP 不存在或数据已超出 RP 保留期。
- 先预览计划，再执行写入。

### 不做

- 不做复杂脚本引擎。
- 不做外部文件导入。
- 不做多测量跨库联动生成。
- 不做复杂图形化模板库。

## 实现步骤

### 1. 后端补能力

**文件：**

- `apps/bridge/influx-client.mjs`
- `apps/bridge/server.mjs`
- `apps/bridge/influx-client.test.mjs`

**任务：**

- 增加批量造数的计划计算逻辑。
- 增加 measurement 存在性探测。
- 增加 RP 风险提示所需的信息解析。
- 增加预览接口。
- 增加执行接口。
- 补单测覆盖：
  - 时间模式解析
  - measurement 不存在
  - RP 提示
  - field 约束校验

**预期产出：**

- 后端能返回"计划结果"。
- 后端能执行确认后的批量写入。
- 单测能覆盖关键边界。

**风险：**

- 时间范围解析不一致。
- RP 解析结果和真实集群配置不一致。
- field 约束表达式过于宽松导致写入异常。

**回滚方式：**

- 先保留现有 query / write 行为不变。
- 新增路由失败时，仅移除新增接口，不影响原有查询功能。

### 2. 前端补入口和弹窗

**文件：**

- `apps/web/src/App.tsx`
- `apps/web/src/api.ts`
- `apps/web/src/types.ts`
- `apps/web/src/styles.css`
- 需要时新增少量局部样式文件

**任务：**

- 左侧工具区新增"批量造数"入口。
- 弹窗中按区块展示：
  - 目标选择
  - 时间范围
  - tag / field 配置
  - 约束规则
  - 预览结果
- 目标选择要联动 database / measurement。
- 时间选择要支持：
  - 最近 N 天
  - 单天
  - 多天
- 预览时展示：
  - 待生成日期
  - 点数估算
  - measurement 是否待创建
  - RP 风险提示
  - 约束摘要
- 执行前二次确认。

**预期产出：**

- 用户能从当前主界面直接进入批量造数。
- 能先看计划，再确认执行。
- 界面不需要跳页。

**风险：**

- 弹窗过重，影响主界面。
- 配置项太多导致新用户看不懂。
- 交互和现有 Schema / 时间转换弹窗风格不一致。

**回滚方式：**

- 先保留主界面原有查询和目录逻辑。
- 新入口和弹窗如果出现问题，可以只下线入口，不动查询主流程。

### 3. 数据模型补齐

**文件：**

- `apps/web/src/types.ts`
- `apps/web/src/workspace.ts`

**任务：**

- 定义时间模式类型。
- 定义 tag / field 配置类型。
- 定义批量造数 plan / execute 请求响应类型。
- 如需要，补工作区保存字段，但不要污染现有查询状态。

**预期产出：**

- 前后端共享类型明确。
- 计划、预览、执行三步的数据结构稳定。

**风险：**

- 类型膨胀。
- 工作区状态过多，影响恢复逻辑。

**回滚方式：**

- 新类型独立命名。
- 不改现有查询工作区版本，除非确有必要。

### 4. 版本号升级

**文件：**

- `package.json`
- `src-tauri/Cargo.toml`
- `src-tauri/tauri.conf.json`
- `CHANGELOG.md`

**任务：**

- 版本号统一改为 `0.5.0`。
- 更新更新日志。
- 在日志里记录：
  - 批量造数入口
  - 时间范围选择
  - 待创建 measurement
  - field 约束
  - RP 风险提示

**预期产出：**

- 构建物版本号一致。
- 用户能从日志看出 0.5.0 做了什么。

**风险：**

- 某处漏改导致版本不一致。

**回滚方式：**

- 版本号集中检查三处配置文件。

### 5. 验证

**文件 / 命令：**

- `npm run test:bridge`
- `npm run test:web`
- 必要时补充单测

**任务：**

- 跑桥接层测试。
- 跑前端测试。
- 检查新增接口是否能处理：
  - measurement 缺失
  - 多天时间范围
  - RP 风险
  - field 约束

**预期产出：**

- 至少保证核心逻辑可回归。
- 不破坏已有查询、Schema、引导和执行记录功能。

**风险：**

- 批量造数逻辑接入后影响现有目录、查询状态。

**回滚方式：**

- 保持改动分层。
- 出问题先关掉新入口，再查后端实现。

## 关键确认点

开始实现前，建议先确认这几件事：

1. measurement 不存在时，是否允许用户在确认后自动创建。
2. field 约束是否只支持简单比较，还是要支持更复杂表达式。
3. tag / field 的默认生成方式是否只保留固定值和随机值。
4. RP 超限时，是直接阻止执行，还是允许强确认后继续。

## 完成标准

满足以下条件即可认为 0.5.0 达标：

- 能选 database 和 measurement。
- 能选单天、多天、最近 N 天。
- measurement 不存在时会标记为待创建。
- field 约束可预览、可校验。
- 能提示 RP 不存在或超出保留期。
- 先预览，再执行。
- 版本号统一为 0.5.0。
